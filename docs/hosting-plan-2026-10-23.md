Обновление версии 0.3: подготовка сервера и команды размещения реализованы локально. Актуальны [пошаговая инструкция](alwaysdata.md) и [повторная проверка исправлений](fixes-2026-10-23.md). Ниже сохранён первоначальный план и сравнение тарифов до реализации.

Проверка тарифов и документации: 23.10.2026. Сейчас имеется локальный commit `1f825f9`; удалённого Git-репозитория и публичного приложения нет. План относится к учебной демонстрации на вымышленных данных. Ничего на внешние площадки в ходе аудита не публиковалось.

## Выбор: alwaysdata Free

Для нынешнего Node.js + SQLite это наименьшая переделка из рассмотренных вариантов. В одном Node-приложении можно обслуживать три интерфейса и общий API. Три независимых платных/бесплатных вычислительных экземпляра не требуются.

Актуальные параметры Free: **0 €/месяц, 1 GB диска, 256 MB RAM, 1/4 CPU, 3 дня резервных копий**. В дисковую квоту входят файлы, почта и базы. Free ограничен адресом аккаунта `alwaysdata.net`, не допускает использования ради прибыли и отдельной функции фоновых Services. [Официальный тариф и ограничения](https://help.alwaysdata.com/en/docs/admin-billing/billing/public-cloud-prices/).

На главной странице указаны регистрация **без банковской карты**, отсутствие срока окончания Free и личное использование. Это отличается от предложения первого бесплатного месяца Plus. Выбирать нужно именно Free. [Описание Free](https://www.alwaysdata.com/en/), [тарифы](https://www.alwaysdata.com/en/offers/).

Некоммерческое учебное демо — целевой сценарий этой рекомендации. Размещение коммерческого пилота для спонсора на Free нельзя автоматически считать разрешённым. Если использование станет коммерческим, потребуется другой тариф/провайдер и отдельный выбор инфраструктуры под реальные медицинские сведения.

### Поместится ли проект

Измерено: существующие исполняемые файлы и ассеты — **2 873 775 байт**, приблизительно 2,9 MB; 35 файлов. В отдельном тестовом процессе базовый Node-сервер занимал **57,9 MiB RSS** без нагрузки. Это не измерение памяти под конкурентной нагрузкой.

Следовательно, по текущему размеру есть большой запас до 1 GB, а базовый процесс помещается в 256 MB. Несколько лёгких интерфейсов и десятки вымышленных профилей ожидаемо поместятся; окончательно проверить после добавления кабинета психиатра и на самом аккаунте. Не размещать здесь записи созвонов, исследовательские PDF, node_modules с ненужными пакетами и исходные материалы кейса. Для текущего приложения установка npm-зависимостей не нужна.

### Почему не другие рассмотренные варианты

| Хост | Ограничение для текущего приложения | Вывод |
| --- | --- | --- |
| alwaysdata Free | 1 GB/256 MB, личное использование, без собственного домена и фоновых Services | Основной вариант учебного стенда |

Cloudflare описал ограничения доступа из РФ в публикации **26 июня 2025 года**; это исторический источник риска, а не проверка всех российских сетей на сегодня. [Официальное сообщение Cloudflare](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet/). Выбор alwaysdata — инженерная оценка применительно к этому коду, не гарантия сетевой доступности провайдера.

## Как разместить все части

Один адрес аккаунта, один процесс и одна сохраняемая база:

```text
https://<account>.alwaysdata.net/                 ВОП
https://<account>.alwaysdata.net/patient/         пациент
https://<account>.alwaysdata.net/psychiatrist/    психиатр, после реализации
https://<account>.alwaysdata.net/api/            общий backend
https://<account>.alwaysdata.net/bot/            необязательный локальный симулятор
```

Кабинет психиатра сейчас отвечает 404. Для него потребуется создать интерфейс и API доступа врача к назначенным профилям. Само наличие каталога и HTML не создаёт медицинскую авторизацию. Настоящий бот работает через Telegram API и HTTPS-webhook общего backend; `/bot/` остаётся веб-демонстрацией диалога.

Один origin упрощает публикацию и взаимодействие компонентов. Пациент должен связываться с данными по проверенной Telegram-идентичности, а врач — через отдельную авторизацию и права. Текущая cookie обеспечивает только тестовый профиль одного браузера.

## Что изменить в коде до первого публичного запуска

Эти настройки **пока не реализованы**. Простое добавление переменных в панель без изменений кода не исправит сервер.

1. **Адрес слушателя.** Использовать IP/HOST и PORT из панели хостинга. Сейчас IP жёстко задан как 127.0.0.1. alwaysdata требует именно выданные адрес и порт. Node 24 поддерживается. [Конфигурация Node.js](https://help.alwaysdata.com/en/docs/web-hosting/languages/nodejs/configuration/).
2. **Публичный origin.** Ввести `PUBLIC_ORIGIN`, разрешённый Host и корректную проверку HTTPS-Origin. Сейчас публичный Host получает 403, а Origin сравнивается с `http://...`. Не выключать проверки целиком.
3. **Постоянный путь базы.** Добавить `DATA_DIR`/`DATABASE_PATH` вне каталога версии кода. Сейчас база лежит в `.data/` рядом с исходниками. Обновление релиза не должно создавать пустую базу или удалять записи.
4. **Режим демонстрации и доступ.** Оставить вымышленные сведения, явно подписать демо-функции, ограничить злоупотребление API. Реальные данные не подключать к публичной cookie-демонстрации.
5. **Telegram.** Добавить проверяемый initData, обработчик Update/webhook с проверкой источника и дедупликацией, связь с пациентом и реальную отправку сообщений. При подключении SDK проверить CSP и поведение Telegram Web. [Официальный процесс Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).
6. **Диагностика.** Добавить неизменяющий состояние `/healthz` и структурированные логи ошибок/решений без токенов и содержимого медицинских заметок. Не использовать выдачу новой сессии `/api/state` как безымянную частую проверку доступности.

Сначала также закрыть ошибки из [аудита](audit-2026-10-23.md). Эти действия не заменяются выбором более дорогого тарифа.

## Регистрация и первый запуск

1. Зарегистрировать alwaysdata Free, подтвердить email и выбрать имя аккаунта. Банковская карта по опубликованному описанию Free не нужна. Фактическая регистрация, доступность имени и возможная дополнительная проверка аккаунта ещё не пройдены.
2. Создать **приватный GitHub-репозиторий** только для каталога `clinical-compass-2026/app`. В Git не должны попадать `.data/`, `.env`, реальные записи и секреты. Локальный Git уже существует. Удалённый адрес пока не настроен.
3. В alwaysdata выбрать **Environment → Node.js → 24**, настроить SSH-ключ. По SSH проверить `node --version` и доступность `node:sqlite`.
4. Создать каталог приложения и постоянный каталог данных. Удобная схема:

```text
/home/<account>/sechenovka/
  current/              код текущего релиза
  shared/data/          demo.sqlite и файлы WAL/SHM
  backups/              согласованные резервные копии базы
```

5. Клонировать репозиторий в `current` через SSH. Для приватного GitHub нужен отдельный read-only deploy key либо иной поддержанный механизм; пароль/токен не помещать в clone URL и Git.
6. В **Web → Sites** создать сайт типа **Node.js**, задать рабочий каталог `.../current`, команду `node /home/<account>/sechenovka/current/server.mjs`, адрес аккаунта и параметры из пункта адаптации. Выданные IP/PORT брать из панели, не подставлять локальный 4173 автоматически.
7. Включить HTTPS и перенаправление HTTP → HTTPS. Сначала проверить `/` и `/patient/`, затем сохранение вымышленного ответа и его наличие после рестарта. Кабинет психиатра появится после добавления соответствующего кода в тот же репозиторий.

Условный контракт окружения после адаптации:

```dotenv
NODE_ENV=production
PUBLIC_ORIGIN=https://<account>.alwaysdata.net
DATA_DIR=/home/<account>/sechenovka/shared/data
DEMO_MODE=true
# HOST/IP и PORT — значения панели alwaysdata
```

`BOT_TOKEN` и другие секреты — только в серверном окружении. Ранее отправленный в переписку токен не переиспользовать; для реального подключения нужен новый. В клиентский JS он не попадает.

## Напоминания на Free

Функция **Services** для отдельных фоновых программ доступна на платных тарифах. Поэтому не строить Free-развёртывание на отдельном бесконечном worker-процессе. [Ограничение Services](https://help.alwaysdata.com/en/docs/web-hosting/services/).

Платформа документирует **Advanced → Scheduled tasks** для периодических команд/URL. Предлагаемая схема: короткая задача раз в минуту вызывает защищённый обработчик напоминаний в общем backend. Доступность и допустимую частоту задачи подтвердить в конкретном Free-аккаунте; сам аккаунт ещё не создан. [Документация задач](https://help.alwaysdata.com/en/docs/web-hosting/tasks/).

Это потребует отдельного защищённого endpoint и выноса проверки расписания из зависимости только от `setInterval`. Дедупликация, завершение задания и подавление оставшихся уведомлений должны оставаться серверными. При таком вызове операции с JSON-состоянием выполняются одним backend; не запускать второй независимый писатель в ту же SQLite без транзакций/CAS, иначе возможна потеря конкурентных обновлений.

Cron запускается в пределах назначенной минуты, а не точно в секунду. Не обещать секундную точность. Сначала проверить тестовую доставку на публичном стенде, затем подключать реальную отправку Telegram. Процесс `setInterval` в нынешнем локальном демо сам по себе не гарантирует доставку при остановленном сервере.

## Обновление после каждой итерации

**Самый простой первый процесс:** локальные изменения → тесты → commit/push в GitHub → `git pull --ff-only` на хостинге → Restart в панели. Базу при этом не трогать. Платформа документирует перезапуск сайта через панель и API. [Перезапуск](https://help.alwaysdata.com/en/docs/web-hosting/sites/restart-a-site/).

После первого стабильного размещения автоматизировать тот же процесс через GitHub Actions: push в `main` → Node 24 + тесты → загрузка/обновление кода по SSH → перезапуск → проверка `/healthz`. Доступы хранить в Secrets, проверять SSH host key и не выдавать секреты workflow из недоверенного PR. Это проектируемая настройка, сейчас pipeline нет. Официальные примеры автоматизации: [Git hooks](https://help.alwaysdata.com/en/blog/2018-02-05-deploy-at-lightning-speed-with-git-hooks/), [webhooks](https://help.alwaysdata.com/en/blog/2023-02-01-devops-react-we-can-be-heroes-just-for-one-app/).

Для аккуратного отката позже можно хранить релизы по commit SHA и менять ссылку `current`; `shared/data` остаётся тем же. Перед миграцией схемы — согласованная резервная копия SQLite. При активном WAL нельзя считать копирование только `demo.sqlite` полноценной свежей копией. Откат кода не должен автоматически откатывать медицинские/тестовые записи.

Перед публикацией новой версии проходить найденные F01–F08 и обычный сквозной сценарий. После публикации — проверять номер версии, сохранение записи, перезапуск без потери данных и отсутствие старых ассетов PWA.

## Приёмка размещения

- Все реализованные страницы и ассеты открываются по HTTPS, без публичного 403 и ошибок CSP.
- Анкета сохраняется; после обновления кода и рестарта ответы остаются на месте.
- Реальный Telegram открывает Mini App; пользователь узнаётся по проверенному initData, а не по имени в неподтверждённом JSON.
- Психиатр после реализации видит только разрешённые профили и исходные данные, пациент — свои.
- Напоминание доставляется в реальный тестовый чат в выбранном поясе; после завершения задания сообщения этого дня прекращаются.
- Один и тот же публичный URL проверен на телефоне в Wi‑Fi/мобильной сети, с VPN и без него. Нынешние localhost-результаты этого не доказывают.
- Секреты отсутствуют в публичных файлах, Git и технических логах; тестовые сведения подписаны как вымышленные.

**Уверенность в выборе: 85%.** Совместимость и опубликованные ограничения проверены. До фактического аккаунта остаются регистрация, возможности Scheduled tasks именно на Free, пробный deploy, ресурсный тест и доступность конкретного публичного домена из нужных сетей. Для текущего небольшого учебного Node/SQLite-стенда это обоснованный первый вариант.
