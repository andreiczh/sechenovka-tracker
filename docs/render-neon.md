# Render Free + Neon Free · версия 0.5

Три интерфейса работают в одном Node.js-сервисе: `/`, `/patient/`, `/psychiatrist/`. `/bot/` — симулятор Telegram, не настоящий бот. Хранилище вынесено в Neon PostgreSQL; перезапуск или обновление Render не должны удалять ответы.

## Почему эта схема

Пользователь отказался заполнять обязательный профиль alwaysdata. Render и Neon доступны через существующий вход GitHub; для выбранных бесплатных ресурсов не используются карта и почтовый адрес. Отдельные платные сервисы, диски и Render Postgres не создаются.

По документации, проверенной 23.10.2026:

- [Render Free](https://render.com/docs/free): 750 часов работы в месяц на workspace, остановка после 15 минут без запросов, холодный запуск может занять около минуты. Локальная файловая система непостоянна. Бесплатная Render Postgres истекает через 30 дней, поэтому не используется.
- [Neon Free](https://neon.com/pricing): $0, без карты и срока окончания; до 100 CU-часов и 1 ГБ хранения на проект в месяц. Тарифные условия следует перепроверять перед расширением пилота.

Это бесплатный демонстрационный стенд с вымышленными данными. Он не обеспечивает клиническое дежурство, медицинскую авторизацию и круглосуточную доставку уведомлений.

## Размещение

1. Создать отдельный приватный GitHub-репозиторий из каталога `app`. Не добавлять `.env.*`, `.data`, `node_modules`, `dist` и результаты тестов.
2. В Neon создать отдельный Free-проект `sechenovka-tracker`, PostgreSQL в Ohio. Сохранить строку подключения только в секретах окружения. Не копировать её в README, чат, URL сайта или клиентский код.
3. В Render создать **Web Service → Free** из этого репозитория, ветка `main`, регион Ohio. Команды: build — `npm ci --ignore-scripts && npm test`, start — `node server.mjs`, health check — `/healthz`.
4. Окружение: `NODE_VERSION=24`, `NODE_ENV=production`, `DEMO_MODE=true`, `REMINDER_SCHEDULER=off`, секрет `DATABASE_URL` из Neon. `PORT`, `RENDER` и `RENDER_EXTERNAL_URL` предоставляет Render. Последний используется для проверки допустимого домена и HTTPS-cookie.
5. Включить обновление после успешных проверок GitHub. Те же параметры описаны в `render.yaml` для Blueprint; ручная настройка не требует Blueprint.
6. Проверить все страницы, новый скрининг, дневник, врачебную запись и повторное чтение после перезапуска/деплоя. Убедиться, что план пациента не содержит внутреннюю клиническую запись врача.

## Что изменено для постоянного хранилища

Сервер работает с асинхронными операциями. PostgreSQL использует проверяемое TLS-соединение, параметризованные запросы и отдельную транзакцию на запрос с блокировкой по демонстрационной сессии. Блокировка общая для перекрывающихся версий сервиса; два одновременных ответа с одной ревизией не перезаписывают друг друга. HTTP-успех отправляется после COMMIT. При ошибке записи возвращается ошибка, прежнее состояние сохраняется.

Таблицы `demo_sessions` и `demo_clinician_workspaces` создаются при запуске без удаления прежних данных. Секрет подключения и содержимое ответов не включаются в журнал ошибок. Проверка `/healthz` не создаёт пациентский профиль.

## Последующие обновления

Локально выполнить `npm ci --ignore-scripts` и `npm test`, проверить изменённый сценарий, затем сделать commit и обычный push в `main`. GitHub Actions запускает проверки; Render обновляет тот же адрес после успешных проверок. Не создавать новый сервис для каждой итерации. Проверять вкладку Events/Logs и `/healthz` после публикации.

При ошибке — вернуть предыдущий успешный deploy в Render или исправить код и повторить push. База остаётся отдельной. Будущие несовместимые изменения схемы требуют отдельной миграции; текущая версия только добавляет таблицы.

Проверка настоящей PostgreSQL включается **отдельно**: `RUN_POSTGRES_TESTS=1 node --env-file=.env.render --test tests/postgres-integration.test.mjs`. Обычные CI-тесты не подключаются к базе стенда. Интеграционная проверка создаёт случайные тестовые сессии и удаляет только их.

## Границы

- Cookie связывает синтетический профиль и демонстрационный кабинет в одном браузере. Это не врачебная авторизация и не передача между реальными людьми.
- Настройка напоминаний и симулятор сохранены; фоновая отправка Telegram не подключена. На спящем бесплатном сервисе нельзя обещать своевременную отправку.
- Все шрифты и изображения локальные. Доступ из РФ проверяется по фактическому опубликованному адресу; результат одной сети не гарантирует доступ у всех операторов.
- Переход к реальным пациентам требует отдельного решения по данным, авторизации, медицинской ответственности и клинической проверке.
